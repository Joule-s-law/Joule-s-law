# 《焦耳定律》游戏策划与程序架构设计

> 技术栈：pnpm + TypeScript + Vite + Vue 3
> 类型：电路搭建 × 增量游戏（Incremental / Idle）

---

## 一、游戏策划

### 1.1 核心循环

```
搭建电路 → 通电做功 → 有效能量换资金 → 购买元件/升级科技
    ↑                                          ↓
    └────────────── 更大、更复杂、更危险的电路 ←──┘
```

资金收入的唯一来源是**元件对外做的有效功**。不同能量形式对应不同的"能量形式资金倍率"，玩家通过"产线优化"科技提升：全局资金倍率、各能量形式倍率、点击产热与冷却。

### 1.2 资金结算公式

每个 tick（固定 100ms，`t = 0.1s`）结算一次：

```
收入 = Σ(各做功元件本tick输出的有效能量 E_i) × 能量形式倍率_i × 全局资金倍率
```

分形式举例：

| 做功形式 | 有效能量定义 | 说明 |
|---|---|---|
| 热量 | `Q = I² · R · t` | 电阻、灯泡的发热部分 |
| 化学能 | 电解池输入电能 `E = U · I · t` | 玩家无需知道材料，通电即收益 |
| 声能 | 蜂鸣器输入电能转化的声功 `W = η · U · I · t` | η 为声转换效率 |
| 动能 | 电动机输出的机械功 | 本身不直接换钱，驱动涡轮发电机 |
| 电能 | 由涡轮发电机等"发电端"产出 | 电是中间资源，驱动其他做功元件 |

> 设计约束：**所有能量转换效率 < 100%**（0.6 ~ 0.9）。能量在形式间闭环流转时必然净损耗，从机制上杜绝永动机；资金只能从"耗散/做功端"产出，而做功端同时也是电路负载（有电阻、耗电），保证电能有真实成本。

### 1.3 电能从哪里来（经济入口）

| 来源 | 机制 | 定位 |
|---|---|---|
| 手摇发电机（初始可买） | 免费提供小电动势，但有内阻与功率上限 | 起步电源 |
| 电池组系列 | 购买价格指数增长，输出功率阶梯提升 | 主要投资方向，控制收入增速 |
| 蒸汽机 + 涡轮发电机 | 热量 → 动能 → 电能的转换链 | 中期"烧钱买热、热转电"的高级玩法 |
| 光电池 | 接收环境亮度 → 输出电流 | 光系统的经济出口 |
| 感应线圈 | 处于变化磁通中产生感应电动势 | 磁系统的经济出口 |
| 二次电池 | 充电存储 / 放电输出（有损耗） | 调峰，不产生资金 |

初始引导（先有鸡还是先有蛋）：

- 玩家初始资金为 0，但拥有一个**免费的**"手指加热"能力：点击鼠标产生 1J 热量 → 直接结算资金（热量倍率很低）。
- 冷却 0.5 秒，产热量与冷却速度均可被"产线优化"提升（有上限，避免压过电路玩法）。
- 攒够钱 → 买手摇发电机 + 一个电阻 → 通电后电阻按 `Q = I²Rt` 持续产热换钱，进入自动循环。

### 1.4 元件清单（按解锁阶段）

所有元件的通用属性：`价格`、`端口数`、`电阻 R`、`额定电流 I_rated`、`行为类型`。

**阶段一：起步**
| 元件 | 行为 | 关键数值 |
|---|---|---|
| 手摇发电机 | 电压源 + 内阻 | EMF 小、功率上限低 |
| 电阻（发热器） | 纯发热换钱 | R 中、I_rated 高 |
| 导线 | 连接，`R = 电阻率 × 长度` | 材料可升级（见 1.5），不损毁（极高 I_rated） |

**阶段二：光与转化**
| 元件 | 行为 | 关键数值 |
|---|---|---|
| 灯泡 | 发热换钱 + 发光（亮度 ∝ 功率） | I_rated 低（易烧） |
| 光电池 | 接收亮度 → 输出电流 | 亮度随距离平方衰减 |
| 电解池 | 通电换钱（化学能倍率高于热倍率） | R 大、I_rated 中 |
| 电池组 | 电压源，价格指数上涨 | 主要投资 |

**阶段三：动能与化学**
| 元件 | 行为 | 关键数值 |
|---|---|---|
| 电动机 | 电能 → 动能 | 需与涡轮机相邻 |
| 涡轮发电机 | 动能 → 电能 | 转换效率 ~0.85 |
| 蒸汽机 | 热量 → 动能 | 需热源供电（吃旁边元件的热） |
| 二次电池 | 充/放电，功率限制 | 调峰工具 |

**阶段四：声与磁**
| 元件 | 行为 | 关键数值 |
|---|---|---|
| 蜂鸣器 | 通电换钱（声能倍率） | 声能倍率最高但 I_rated 极低 |
| 麦克风 | 接收声能 → 输出电流 | 与蜂鸣器构成"声传电"（效率低，仅特殊布局用） |
| 通电线圈 | 电流 → 产生磁感应强度 B | B ∝ 匝数 × I |
| 感应线圈 | 变化磁通 → 感应电动势 | 法拉第定律，可做"隔离变压器" |

**辅助**
| 元件 | 行为 |
|---|---|
| 保险丝 | 超流先熔断自己（廉价），保护贵重元件 |
| 开关 | 通断控制，构建自动化逻辑的雏形 |

### 1.5 导线材料与电阻率

- 导线不是理想导线，而是真实元件：`R = 电阻率 × 长度`（每段导线按跨接长度计算）。长距离输电有真实的热损耗（损耗同时按热量做功换钱，所以短线路是纯亏，紧凑布局有价值）。
- 玩家通过科技解锁并升级导线材料（数值非现实值，方便玩家直观比较）：

| 材料 | 电阻率 | 解锁阶段 |
|---|---|---|
| 铜导线 | 1e-8 | 初始 |
| 银导线 | 1e-9 | 中期科技 |
| 超导体 | 0 | 后期科技 |

- 超导体 R = 0 的双刃剑：导线零损耗、零发热，但也失去"天然限流"——短路电流完全由电源内阻限制，高级电源 + 超导线反而放大烧毁风险，与损毁系统联动形成后期风险管理玩法。
- 已铺导线可花钱更换材料（逐条或全板替换），旧导线不返还，鼓励前期不要过度铺线。

### 1.6 光线与磁场系统

两者都不脱离电力经济——它们是**能量的无线/隔离传输通道**，且转换效率低于导线直连，只在特定布局（跨区域供电、隔离保护）下有优势：

- **光线**：属性为亮度。光源（灯泡）按功率发光，亮度在网格上按距离衰减扩散；光电池采样所在格亮度转为电流。投资方向是"更大功率灯泡 + 更高光电池效率"。
- **磁场**：属性为磁感应强度 B、磁通量 Φ。通电线圈按电流产生 B；感应线圈按 `dΦ/dt` 产生感应电动势。玩法：原副线圈隔离输电（原线圈侧烧毁不影响副线圈侧）、以及后期"磁场放大器"科技。

### 1.7 额定电流与损毁（风险管理玩法）

- 每个元件有 `I_rated`。实际电流超过额定值时开始积累"过载热量"，超过容忍时间（约 1 秒）即损毁。
- 损毁返还购买价的 **10%**。
- 电路设计因此有真实取舍：电阻越小电流越大收入越高，但越容易烧；保险丝是廉价牺牲品。
- UI 需实时显示每个元件的电流/额定比（安全 / 过载预警 / 即将损毁）。

### 1.8 产线优化（科技树）

原则：**数值提升是杠杆，不是答案**——任何科技的收益上限不应超过"优化电路拓扑"一个数量级。

| 分支 | 效果 | 限制 |
|---|---|---|
| 点火优化 | 点击产热 +、冷却 - | 点击收入占比较低（封顶） |
| 全局倍率 | 总资金倍率 + | 便宜但增量小 |
| 形式倍率 | 热/化/声/光/磁 各自倍率 + | 引导玩家专精某条产线 |
| 材料学 | 全体元件 I_rated + | 降低烧毁风险 |
| 导电材料 | 解锁银导线、超导体 | 需搭配"材料学"才安全 |
| 转换效率 | 蒸汽机/涡轮/光电池等 η + | 提升转换链价值 |
| 解锁项 | 新元件、保险丝、开关、磁场系统 | 结构性解锁 |

### 1.9 平衡红线

1. 任何能量闭环净效率 < 100%，禁止无电源的钱自增长。
2. 电源（电池组）价格指数增长（×1.15/个），功率线性增长 → 收入增速天然受控。
3. 点击收入始终 ≤ 同期自动收入的 10%。
4. 高倍率形式（声、化）搭配低 I_rated → 高收益伴随高烧毁风险。

## 二、程序架构

### 2.1 总体分层

核心原则：**模拟内核（core）是纯 TypeScript，零 Vue 依赖、零 DOM 依赖**，可以被完整单元测试、序列化、甚至跑在 Web Worker 里。Vue 只做视图与交互桥接。

```
┌─────────────────────────────────────────┐
│  Vue UI 层                              │
│  面板 / 商店 / 科技树 / Vue 响应式状态    │
├─────────────────────────────────────────┤
│  Bridge（Pinia stores）                 │
│  把 core 的快照映射为 reactive 状态，    │
│  把 UI 指令（买元件/连端口/升科技）转发 core │
├─────────────────────────────────────────┤
│  core 模拟内核（纯 TS）                  │
│  Tick 循环 → 电路求解 → 能量账本 → 经济结算 │
└─────────────────────────────────────────┘
```

### 2.3 核心抽象：数据定义 + 行为类 + 注册表（关键扩展点）

**设计思想：把"元件是什么"（数据）和"元件做什么"（行为）彻底分离。**

新增一个元件的完整成本 = 1 个数据文件 +（可选）1 个行为类 + 1 行注册，无需碰求解器、经济、UI 的任何代码。

```ts
// ComponentDefinition.ts —— 纯数据
export interface ComponentDefinition {
  id: string
  displayName: string
  price: number
  portCount: number
  resistance: number
  ratedCurrent: number
  behaviorId: BehaviorId        // 指向行为类
  behaviorParams: Record<string, number>  // 行为参数（转换效率、亮度系数等）
  unlockTechId?: string         // 需要哪个科技解锁
  assetId: string               // 图标/贴图
}
```

```ts
// BaseComponent.ts —— 运行时实例
export abstract class BaseComponent {
  readonly def: ComponentDefinition
  readonly ports: Port[]
  abstract getResistance(): number   // 每tick由求解器调用，返回"当前"电阻（非定值）
  abstract buildCircuitModel(model: MnaModel, dt: number): void  // 向求解器贡献 电导/电源
  abstract onTick(ctx: TickContext): void                        // 能量转换、场发射、过载积累
  // TickContext 提供：当前电流、delta、EnergyLedger、FieldGrid、经济倍率
}
```

`getResistance()` 是电阻的**唯一事实来源**：定义里的 `resistance` 只是初始/基准值，实际每 tick 的电阻由元件自身决定（导线 = 电阻率 × 长度、二次电池 = 充/放电状态不同内阻、未来可扩展热敏/光敏元件）。求解流程因此固定为"先收集所有元件的 `getResistance()`，再建矩阵"，元件在 `onTick` 中更新自身状态、下一 tick 生效，避免同一 tick 内状态与求解互相污染。

行为类按**能力维度**拆分而非按元件拆分，并用组合复用：

```ts
// 例：灯泡 = HeaterBehavior(发热换钱) + FieldSourceBehavior(发光)
// 例：蒸汽机 = ConverterBehavior(热→动能) ，涡轮 = ConverterBehavior(动能→电)
```

`ConverterBehavior` 是最重要的通用行为：一个二端口元件，输入侧表现为电阻（吃电），输出侧按 `η × 输入能量` 产出目标能量形式并写入 EnergyLedger。**电解池、蜂鸣器、电动机、蒸汽机、涡轮发电机全部是这一个类的不同参数实例**，这正是抽象带来的扩展效率。

### 2.4 电路求解（MNA）

- 电路建模为节点图：元件的每个 Port 连接到节点。
- 每 tick 流程：① 遍历元件调用 `getResistance()` 收集当前电阻 → ② 重建 MNA 矩阵 `G·v = i`（电阻元件贡献导纳 `g = 1/R`，电压源贡献附加方程）→ ③ 求解输出每条支路电流 → 写回元件实例，供行为层使用。
- **零电阻特判（超导体）**：`R = 0` 会使导纳发散，矩阵奇异。处理方式：求解前做"零电阻支路的节点合并"（把超导线两端合并为同一节点），数值兜底用极小 ε（1e-9 Ω）防止病态矩阵。这比给超导体硬塞一个假电阻更干净，也让"超导短路"在数学上真实成立。
- 图规模（几十~几百元件）下高斯消元完全够用；后期元件数量大时可移入 Web Worker。

### 2.5 能量账本与经济结算

```
每 tick 流程（Simulation.tick）：
1. 重建/复用电路矩阵 → MNASolver.solve() → 各元件电流
2. 各元件 onTick：
   - 行为层做能量转换（读电流 → 写 EnergyLedger）
   - 场层发射/采样（灯泡发光、光电池取光）
   - 过载检测（I > I_rated 累积过载热量，超时销毁 → 返还10%）
3. Economy.settle()：
   资金 += Σ(账本各项 × 形式倍率 × 全局倍率)
4. 清空账本，进入下一 tick
```

`EnergyLedger` 是能量与钱之间的唯一桥梁：任何行为不允许直接改资金，只能向账本记账，保证公式统一、便于调试和数值统计面板。

### 2.6 与 Vue 的桥接

- `TickLoop` 以固定 10Hz 跑模拟；Pinia store 订阅 core 的**快照事件**（每 tick 或节流 4Hz）刷新响应式状态。
- 电路板渲染走 Canvas（`BoardCanvas.ts`），直接读 core 数据结构，绕过 Vue 响应式——几百个元件 + 连线在响应式系统里渲染代价过高。
- UI → core 的指令全部通过 `Simulation` 暴露的命令方法（`placeComponent` / `connectPorts` / `buyTech` / `sellComponent`），UI 层不直接改 core 内部状态。

### 2.7 存档

- `SaveService` 序列化内容：资金、科技状态、元件（id + 位置 + 连接关系 + 电池电量）、倍率。电路图与元件定义按 id 引用，重新载入后重建。
- 版本号字段 + 迁移函数数组，应对定义变更。
- 每 10 秒自动存 + 页面卸载时存。

### 2.8 新增元件的标准流程（扩展性验收）

以"电磁炉（吃电产热换钱，效率高于普通电阻）"为例：

1. 新建 `definitions/induction_cooker.ts`：`{ id, price, resistance, ratedCurrent, behaviorId: 'heater', behaviorParams: { heatPerJouleBonus: 1.5 } }`
2. 若现有行为不够表达，才新增行为类并实现 `buildCircuitModel` + `onTick`。
3. 在 `componentRegistry` 注册，绑定解锁科技 id。
4. 完成——求解器、经济结算、UI 商店、存档全部自动生效。
